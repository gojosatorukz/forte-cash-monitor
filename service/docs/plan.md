- API contract (exact; jury tests automatically):
  - `POST /api/v1/analyze` — multipart field `file` (.mov typical ~30 MB; accept up to 200 MB, reject larger with 413) → `200 {"job_id": "<str>"}` (extra fields allowed, e.g. `status`).
  - `GET /api/v1/jobs/{job_id}` → `{"job_id", "status": "processing"|"done"|"failed", "verdict": "violation"|"no_violation"|null, "violations": [{"type", "timecode_sec": float, "description", "evidence_frames": [{"timestamp_sec": float, "image_base64": "<JPEG base64, no data: prefix>"}]}]}`. Unknown job → 404. While processing: verdict null, violations []. Failed: `error` string field, verdict null.
  - Extra per-violation fields (encouraged): `end_sec`, `confidence` (0..1), `title_ru`, `rule: {document, point, quote, url}` (list `rules` also ok). Extra job fields: `progress` (0..1), `stage` (RU text), `error`, `created_at`, `finished_at`, `video_meta`, `filename`, `partial` (bool, true if timeout cut it short).
  - Both `/api/v1/*` routes require header `X-API-Key` equal to env `API_KEY` (default `forte-datathon-2026` if unset, log a warning); missing/wrong → 401 JSON.
  - Internal UI routes under `/ui-api/*` (no key): `POST /ui-api/analyze`, `GET /ui-api/jobs/{id}`, `GET /ui-api/jobs/{id}/video` (streams the uploaded video with HTTP Range support so `<video>` can seek), `GET /ui-api/jobs` (recent jobs list), `GET /ui-api/rules`. Same payloads as the public API.
  - `GET /healthz` → `{"ok": true}`.
- Data dir: env `DATA_DIR` (default `./data`): `data/uploads/<job_id>/<original-safe-name>`, `data/jobs/<job_id>.json` (atomic write: temp + os.replace).
- Single background worker thread, FIFO queue; on startup, re-enqueue jobs left in `processing` state (or mark failed with "interrupted by restart" if their upload is missing). Done/failed results survive restart.
- Hard time budget: env `JOB_TIMEOUT_SEC` default 270. The analyzer receives a deadline; at the deadline the worker finalizes with the best partial result (`partial: true`), never exceeding the budget. Analyzer exceptions → `failed` with message, unless violations were already added to `partial` — then `done` + `partial: true` + `meta.analyzer_error` (Ruling R1).
- Analyzer interface (`app/analyzers/base.py`):
  ```python
  ProgressCb = Callable[[float, str], None]   # fraction 0..1, stage text (RU)
  class Analyzer(Protocol):
      name: str
      def analyze(self, video_path: Path, progress_cb: ProgressCb, deadline: float, partial: PartialSink) -> AnalysisResult: ...
  ```
  `deadline` is a `time.monotonic()` value; analyzers should check `time.monotonic() > deadline` and return what they have. `PartialSink` is an object with `.add(violation)` so the worker can return accumulated violations if the analyzer overruns (worker runs the analyzer in a thread and stops waiting at deadline). Selected by env `ANALYZER` = dotted path `module:Class`, default `app.analyzers.stub:StubAnalyzer`. Analyzer instance is created once (at worker start) so heavy models load once.
- Result model: `AnalysisResult{verdict, violations: list[Violation], meta: dict}`; `Violation{type, timecode_sec, end_sec?, confidence?, description, evidence_frames: list[EvidenceFrame]}` — analyzers emit `type` (rule KB id) and frames; the service attaches `title_ru` and `rule` from `rules.json`. **Citations come only from `rules.json`**: the service drops/ignores any citation supplied by an analyzer; a violation whose `type` is not in rules.json is mapped to KB type `other_suspicious` (must exist) keeping the analyzer's description. Verdict is recomputed by the service: `violation` iff ≥1 violation.
- `rules.json` (`app/rules.json`): `{ "<type_id>": {"title_ru", "title_en", "description_template" (RU, may use {t} placeholders), "citations": [{"document", "point", "quote", "url"}], "placeholder": true} }`. Placeholder content now, clearly marked, types: `cash_unattended`, `safe_left_open`, `unauthorized_person`, `cash_out_of_camera`, `bag_unsealed`, `other_suspicious`. Loaded once at startup, validated (pydantic).
- Video utilities (`app/video.py`): `probe(path) -> VideoMeta{duration_sec, fps, width, height, rotation, codec, frame_count}` via ffprobe JSON (handles rotation side-data / tags; width/height reported as displayed, i.e. after rotation); `frame_at(path, t_sec, max_side=960) -> np.ndarray BGR` (ffmpeg seek, rotation applied — ffmpeg autorotates by default; must work with Cyrillic paths — use ffmpeg subprocess with argv list, never cv2.imread/VideoCapture on paths); `iter_frames(path, fps, max_side=...)` generator of `(t, frame)` using ffmpeg pipe raw bgr24; `jpeg_b64(frame, quality=85) -> str` (cv2.imencode is fine).
- Debug mode: env `STUB_DEBUG=1` → stub emits one fake violation (`type: other_suspicious`, description clearly says it's a demo/test) at the video midpoint with 2 real evidence frames. Otherwise stub returns `no_violation`, violations [].
- UI: Russian language, served at `/` from `app/static/` (plain HTML/CSS/vanilla JS, no build step, no CDN — must work offline). Bank-like, clean, professional.
- Tests: pytest in `tests/`, use a tiny generated test video (ffmpeg `testsrc` 3 s, written to tmp, also one copy with a Cyrillic filename) — tests must not depend on the dataset path. Use FastAPI TestClient; worker must be drivable in tests (wait-until-done helper with timeout).
