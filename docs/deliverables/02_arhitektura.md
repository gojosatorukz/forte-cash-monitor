# 2. Архитектура, подход и модели

## 2.1. Идея в одном абзаце

Обучающая выборка построена **парами**: тот же кассир, та же сцена, но в одном видео процедура выполнена верно, а в другом
**пропущен один шаг** или в конце остаётся неправильное состояние. Сами действия (кассир вышел, открыл сейф, вошёл посетитель,
передал сумку) встречаются и в чистых видео. Поэтому мы не ищем «подозрительные действия». Мы **находим контрольные точки**
(кассир уходит, меняется клиент, закончилась передача сумки) и **проверяем состояние сцены в этот момент** по правилам из НПА РК.
Детектор действий без контекста давал бы ложные срабатывания на каждом чистом видео.

## 2.2. Схема

```
            ┌──────────── Веб-интерфейс (RU) ────────────┐      REST API (X-API-Key)
            │ загрузка · прогресс · плеер с метками ·      │      POST /api/v1/analyze
            │ кадры · цитаты НПА · история                 │      GET  /api/v1/jobs/{id}
            └───────────────────┬─────────────────────────┘                │
                                ▼                                         ▼
                 FastAPI + uvicorn · очередь задач (FIFO, 1 воркер) · JSON-хранилище задач
                 бюджет 270/280 с с момента отправки · частичный результат при таймауте
                                │  analyze(video, progress_cb, deadline, partial)
                                ▼
 ┌──────────────────────────── Детектор (forte_detector) ─────────────────────────────┐
 │ 1. Декодирование ffmpeg, ~4 кадра/с                                                │
 │ 2. Восприятие: люди (RT-DETRv2) + трекинг (ByteTrack) → роли и зоны из данных      │
 │    (кассир/клиент/инкассатор, место кассира, дверь), без жёстких координат         │
 │ 3. Таймлайн контрольных точек: уход кассира, смена клиента, визит инкассатора…     │
 │ 4. Пробы состояния в точках: дешёвое CV + open-vocab детектор + вопросы к VLM      │
 │    (деньги на столе? сейф открыт? экран включён? дверь открыта? телефон?)          │
 │ 5. Движок правил T1…T15 → события: тип, интервал, таймкод, кадры, уверенность      │
 │ 6. Аномалия CV вне правил → T99 (низкая уверенность, служебный список)             │
 └──────────────────────────────────────┬─────────────────────────────────────────────┘
                                        ▼
            Справочник rules.json (типы + дословные цитаты НПА) → карточка нарушения
            (цитаты подставляет сервис; модель не может придумать ссылку)

  VLM: llama.cpp llama-server (локально, 127.0.0.1:8090) · Qwen3-VL-Instruct GGUF
```

Статус компонентов на момент написания:
- **Сервис** (FastAPI, очередь, UI, API, 88 тестов) работает.
- **Детектор:** полный конвейер (восприятие → пробы → движок правил → VLM) работает в продакшене, версия `9f8d3b9`.
  Предварительно на 42 открытых видео: полнота 19/22; ложных срабатываний 3/20 — все три T15 «клиент без документа» на роликах,
  которые организаторы считают чистыми (на остальных 16 — 0); перекрёстная проверка 9/11 + 9/11
  (подробно — документ 5; финальный прогон после 08:00 в день проверки).
- **VLM:** выбран Qwen3-VL-4B-Instruct Q4_K_M. Версия 8B проверена и отклонена: точность не выше, чем у 4B.

## 2.3. Компоненты

### Сервис (`service/`)
- **FastAPI + uvicorn**, одна машина, один процесс. Очередь FIFO с одним воркером: так GPU не делится между задачами.
- **Бюджет времени.** Отсчёт идёт с момента отправки. Плановый дедлайн 270 с, жёсткий 280 с (лимит жюри 300 с).
  Анализатор складывает подтверждённые нарушения в `partial` по мере нахождения, поэтому при таймауте задача
  завершается со статусом `done`, флагом `partial: true` и уже найденными нарушениями.
- **Доступ.** Веб-интерфейс закрыт паролем (`/login`, подписанная cookie сессии, блокировка после 20 неверных попыток за 5 минут с одного клиента; при пароле короче 12 символов или `change-me` интерфейс
  отключается; HSTS при работе по HTTPS);
  API `/api/v1/*` — ключом `X-API-Key`.
- **Человек в контуре.** Специалист подтверждает или отклоняет каждое нарушение и выносит итоговое решение; сервис формирует
  печатный акт проверки (`/act.html`), а решения выгружаются как размеченная обратная связь (`feedback.jsonl`) для дообучения
  и настройки порогов. Сервис формирует подозрение, решение принимает человек.
- **Устойчивость.** Задачи хранятся в JSON и переживают перезапуск: незавершённые ставятся в очередь заново.
  Битый файл даёт понятную ошибку `failed`, а не пустой ответ.
- **Нормативка.** Тип нарушения, название и цитаты берутся **только** из `rules.json`. Цитаты, которые вернул анализатор,
  отбрасываются. Вердикт пересчитывается сервисом: `violation` ⇔ есть хотя бы одно нарушение.
- **Видео:** ffmpeg/ffprobe. Поддерживаются кириллица в путях (`Х-17.mov`), метаданные поворота, `.mov` и `.mp4`.

### Детектор (`detector/`)
1. **Восприятие.** Детектор людей RT-DETRv2-S (`PekingU/rtdetr_v2_r18vd`, Apache-2.0, через `transformers`) с трекингом
   ByteTrack (`supervision`, MIT). Из траекторий определяются роли: кто сидит на месте кассира, кто подходит к окну,
   кто приносит сумку. Зоны (место кассира, дверь) **выводятся из данных конкретного видео**, а не задаются пикселями:
   финальное видео снято с другого ракурса.
2. **Контрольные точки:** уход и возвращение кассира, появление следующего клиента, уход клиента, визит инкассатора,
   работа с сейфом.
3. **Пробы состояния** в окне вокруг каждой точки. Три механизма:

   | Механизм | Что делает | Пробы |
   |---|---|---|
   | Классическое CV | считается напрямую по пикселям | дверь открыта (разница с кадром закрытой двери в зоне двери); камера перекрыта (контуры и однородность кадра) |
   | OWLv2 (open-vocab) | **только калибровка**: один раз на видео, по 1–3 кадрам находит зоны сейфа, двери, ноутбука, счётной машины, стола; сам на вопросы не отвечает | — |
   | VLM по вырезанной зоне | узкий вопрос по зоне, найденной OWLv2 (если зона не найдена — по всему кадру) | стол: деньги на столе, сумка, штампы/журнал, личные вещи, предъявлен документ; ноутбук: экран включён и не заблокирован; сейф: дверца открыта, ключ в замке |
   | VLM по кадру целиком | узкий вопрос по 1–3 кадрам | телефон, еда/напиток, используется счётная машина, деньги к телу, число людей |

   Обнаружения RT-DETR (телефон, чашка, сумка) используются только как запасное подтверждение, если VLM не ответила, и с
   пониженным весом.
4. **Движок правил** — детерминированные правила по таблице типов (документ 4). Пример T1: «кассир вышел за дверь И
   на столе деньги/сумка И никого нет».
   Для каждого события сохраняются интервал (начало–конец), опорный таймкод, 1–3 кадра-доказательства
   и **две уверенности**: `fact_conf` (насколько уверенно виден факт) и `legal_conf` (насколько прочна связь с нормой,
   из справочника). `legal_conf` — порядковая шкала (`high` 0,9 / `medium` 0,7 / `low` 0,4), а не вероятность.
5. **VLM** (Qwen3-VL-4B-Instruct, GGUF Q4_K_M, локально через llama.cpp `llama-server`, `--image-min-tokens 1024`).
   Момент предлагает CV, а VLM отвечает на **один узкий вопрос «да/нет» за вызов** по 1–3 ключевым кадрам или
   вырезанной области: «ноутбук заблокирован?», «на столе деньги, рядом никого?», «сколько людей?».
   Целостную классификацию отрезка и ответ сразу на много полей в одном вызове мы проверили и отказались от них:
   модель с ними не справляется. Состояние двери определяется только через CV: VLM почти всегда отвечает «открыта».
   Латентность на ноутбуке с RTX 3060: 0,6–1,8 с на вопрос, 13–40 вопросов на видео (предварительно).
   Свободного или целостного прохода VLM нет.
   На RTX 5080 вопрос занимает около 0,8 с (медиана; 95-й перцентиль 1,1 с), примерно вдвое быстрее ноутбука.
   **T99 «иное подозрительное»** в текущей версии строится по одной аномалии CV: человек, не являющийся кассиром,
   подходит к рабочему месту кассира, когда кассира в помещении нет. Уверенность такого события намеренно низкая (0,18 при
   пороге показа 0,25): оно сохраняется в служебном списке `meta.low_conf` ответа, но **не попадает в список нарушений и
   не меняет вердикт** — чтобы одна аномалия без подтверждения не давала ложного срабатывания.
6. **Рабочая точка — полнота прежде всего.** Организаторы уточнили (17.10.2026): пропуск нарушения недопустим, ложные
   срабатывания допустимы — их отсекает проверяющий. Поэтому порог подбирается на 42 открытых видео так, чтобы не потерять
   ни одного найденного нарушения, а ложных срабатываний было не больше 6 из 20 чистых. Если признак слабый, но есть,
   событие всё равно выдаётся, с низкой `fact_conf`, а не замалчивается.
7. **Доказательства.** По каждому нарушению сервис вырезает короткий MP4-фрагмент (H.264, вокруг события, не длиннее 8 с),
   доступный по `clip_url`. Детектор передаёт для кадров рамки `boxes` (нормированные координаты, подпись, вид); сервис
   рисует их красным с подписью роли («кассир», «посетитель») на первом и третьем кадре. Второй кадр — тот же момент, что
   и первый, без разметки. На видеофрагмент рамки не накладываются.
   Сейчас размечаются только люди; рамки предметов и зон (деньги, дверь, сейф, экран) в разработке.
   Рамки обозначают роль, а не личность: лица не распознаются.

### Оценка и устойчивость (`detector/eval`, `robust/`)
- Инструмент оценки на 42 видео считает точность вердикта, полноту, долю ложных срабатываний, попадание таймкода
  (±3 с, ±5 с) и попадание типа. Дубликаты X-4/X-47 и X-5/X-48 при подборе порогов держатся в одной группе.
- Проверка переноса на новый ракурс: синтетические варианты — перекодирование, зеркало, поворот камеры по горизонтали и
  вертикали, увеличение, сдвиг кадра, поля, поворот 90°, яркость, затемнение, низкий контраст, размытие, а также их комбинация
  «новая камера» (`status_robust.md`). Синтетика имитирует поворот камеры, но не её перенос в другую точку комнаты.
  Сценарий собственных съёмок с ракурсов A–E подготовлен (`docs/recording_guide.md`); свои записи — только для проверки,
  не для обучения.

## 2.5. Гарантия локальности

- **Никаких облачных AI API.** Все модели (детектор, трекер, VLM) запускаются на машине сервиса. VLM-сервер слушает
  только `127.0.0.1`.
- **Сеть нужна один раз**, чтобы скачать веса. После этого сервис работает без интернета, включая веб-интерфейс:
  сторонних CDN у него нет.
- **Видео не покидает машину.** Файлы хранятся в `DATA_DIR`. Публикация наружу: https://forte.incode.kz → Caddy на сервере команды →
  обратный SSH-туннель → машина сервиса (документ 1). Сервер команды только пробрасывает HTTPS-запросы жюри; моделей и анализа
  на нём нет, AI вне машины сервиса не используется. Запасной вариант — cloudflared quick tunnel, тоже только транспорт.
- **Нет распознавания лиц и идентификации людей.** Роли (кассир, клиент, инкассатор) определяются по положению и
  поведению. Звук не используется.
- **Работа без интернета.** На рабочей машине сервис запущен с `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `UV_OFFLINE=1`:
  модели загружаются только из локального кэша, проверка офлайн-загрузки пройдена (`docs/status_deploy.md`).

Бюджет: лимит жюри — 5 минут на видео; жёсткий предел сервиса — 280 с; цель детектора — ≤ 180 с на видео.
Отдельные замеры на RTX 5080 через публичный API: X-17 (видео 15 с) — анализ 8,9 с, 17 вызовов VLM; X-43 (23 с) — 10,0 с, 13 вызовов.
Самое длинное открытое видео X-14 (142,5 с): 28,2 с от начала загрузки до результата через https://forte.incode.kz, из них 8,3 с загрузка
(`docs/status_deploy.md`). Запас до лимита жюри (300 с) — более чем десятикратный.
